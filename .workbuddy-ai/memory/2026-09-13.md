# 2026-09-13

## 定位「点击游戏内按钮轻微卡顿」根因（macOS WebKit 大厅）

症状：单实例、最低画质、帧率 60/90 均复现；多开时其他实例一起掉帧；
iOS 端不复现；隔几秒点一次又卡。据此排除渲染/帧率/多开资源竞争，
锁定为「每次点击固定触发的 App 进程主线程开销」。

根因定位（ios/Shell/MacWebKitGameWindow.swift）：

1. `MacGameSchemeHandler.respond`（:1182）对所有响应硬编码
   `"Cache-Control": "no-store"` → WebKit 缓存被彻底禁用，
   每个资源都要回 App 进程走一遍 CDN 层，第二次点击也命中不了 WebKit 缓存。
   注：加这个头本意只是为了让 Fetch/XHR 拿到 status 200，no-store 是副作用。
2. `webView(_:start:)`（:1079-1081）本地资源用
   `Data(contentsOf: localURL)` 同步读盘，且 bundle 资源没有内存缓存层。
3. 远程分支 `Task { @MainActor }`（:1093）把请求与主线程的 respond 绑在一起；
   `MacGameSettingsStore.setValue/flush`（:244/:269）用 `queue.sync`，
   而调用方是主线程上的 `userContentController` 回调 → 主线程被磁盘 IO 阻塞，
   这正是「多开时其他实例一起掉帧」的原因（所有实例共用 App 主线程）。

次要放大项：调试级别下每次点击输出数十条 NSLog（同步写 unified log）；
`ios2-web-boot.js` 的 `runtimeMemorySnapshot` 每次面板切换同步遍历节点树
（nodes 达 5880）+ `cc.sys.garbageCollect()` 强制 GC（STW）。

## 已落地修复（ios/Shell/MacWebKitGameWindow.swift，xcodebuild BUILD SUCCEEDED）

## HSDK 响应批量化（MacWebKitGameWindow.swift）

`sendHSDKMessage` 原来每来一个请求就单独 `evaluateJavaScript` 一次。
一次点击会连发二十来个 `report_log_post`，即二十次跨进程往返 + 主线程回调，
全挤在点击后一两帧内。改为：

- `batchableHSDKActions = ["report_log_post"]`：纯上报入队，下一个主 RunLoop
  合并成一次 `evaluateJavaScript`（脚本里连续调 N 次 `HSDK.onMessage`）。
- 登录 / `sdk-get-userId` 等有依赖的仍立即发，不参与合并。
- 批量只打一条 `HSDK batch response sent: N call(s)`，顺带减少日志。

**关键区分**：调低日志等级无效 ≠ 这条路径没开销。日志只是旁路观测，
IPC + JSON 编解码 + 主线程调度照旧发生。

## 一键关分组崩溃：WKURLSchemeTask 已停止（本轮追加）

- 现象：分组整体启动后一键关闭整个分组，App 抛 `NSInternalInconsistencyException: This task has already been stopped`，
  堆栈落在 `MacGameSchemeHandler.respond(...)`（文件 `ios/Shell/MacWebKitGameWindow.swift`）。日志里的
  linkd / pboard / launchservicesd / coreservicesd 报错是 WebContent 沙盒噪音，与本次崩溃无关。
- 根因：`webView(_:start:)` 里每个远程资源都 `await` 共享 CDN actor，期间的 CDN 请求由 `MacCDNResourceManager` 持有、
  并不随窗口取消；一键关分组时 `stop()` → `stopLoading()` 让 WebKit 把所有在途 task 置为 stopped，
  等 await 回来再 `didReceive/didFinish`（或 `didFailWithError`）就会命中这个断言。实例越多、请求越密越容易复现。
- 修法（全部在 `MacGameSchemeHandler`）：
  - 新增 `isStopped` 与 `stopAll()`；`MacWebKitGameView.stop()` 在 `stopLoading()` 前调用 `schemeHandler.stopAll()`。
  - `webView(_:start:)` 开头 `isStopped` 直接返回；`respond(_:...)` 开头再兜一道（pending 中且未 stop 才回调）。
  - await 之后不再无条件 respond / fail：先 `pending.removeValue(forKey:)`，取不到说明任务已被 stop 或实例已释放，直接丢弃
    （原来 handler 已释放的分支是 `MacLog.error`，改为 debug，属于正常关闭路径，不该刷错误日志）。
  - `reportStalePendingTasks()` 在 `isStopped` 时不再误报悬挂。
- 校验：macOS scheme 用 `/tmp/ios2mac-scheme-fix` 构建 `BUILD SUCCEEDED`；未刷新仓库内构建产物。
- 收敛（同轮）：闸门统一收进 `respond` / `fail` 两个出口（只在 `fail` 里摘 pending，`respond` 只校验不摘，避免同一 task 被回传两次），
  本地资源读盘失败也改走 `fail`，不再直接 `didFailWithError`。再次构建 `BUILD SUCCEEDED`。
- 回归与修正（同轮）：上一版按**实例粒度**（`isStopped`）一刀切丢弃回调，把还没被 WebKit 停止的任务一起拦掉，
  结果主文档 `ios2-game://app/index.html` 也被抑制 → 全部实例白屏「无法登录」。
  改为按**任务粒度**判定：新增 `stoppedTasks: Set<ObjectIdentifier>`，只吞掉 `webView(_:stop:)` 明确通知过的任务；
  `stopAll()` 先对仍在 pending 的任务正常 `didFailWithError` 收尾，再把剩余 token 并入 `stoppedTasks` 后清空，
  之后 `stopLoading()` 停止的那些由迟到的 continuation 自行命中抑制分支。同时 `fail` 对未登记任务先补登记再走闸门
  （否则该请求永远无人收尾）。另加 `stopAll` 的 debug 调用栈日志，便于定位是谁提前 stop。
- 校验：macOS scheme 用 `/tmp/ios2mac-scheme-fix` 三次构建 `BUILD SUCCEEDED`；未刷新仓库内构建产物。

## 渲染「元素不全」根治（多开 + 来回切场景，概率性随机实例）

现象：单开概率低，多开（10 个）概率高；来回切场景几次后某个场景缺元素；
**实例随机**，同一批资源有的实例好有的坏。

### 核心结论：Cocos 没有「渲染失败」，只有「不画」

一个节点能被画出来要同时满足：① activeInHierarchy ② opacity>0 ③ 有 spriteFrame
④ `texture.loaded === true`。任一不成立，assembler 就 `if (!texture.loaded) return;`
**静默跳过**——不抛错、不告警、不重试。所以这类问题在日志里天然无痕，只能主动
遍历场景树去问「有几个本该画的节点画不出来」。

### 根因：引用计数驱动的自动释放，与场景切换存在竞态

引擎 `release-manager`（ios2-web-cocos2d.js ~22650）实证：
- `Asset.decRef(autoRelease)`：`!1 !== t` 时才 `tryRelease(this)`
- `tryRelease(asset, force)`：force 立即 free，否则入队，**下一帧 `_free()`**
- `_free(t, e)`：`!( !e && t.refCount > 0 && u(t) > 0 )` → refCount 归零即 `destroy()`，
  并**递归** `o.decRef(!1), m._free(o, !1)` 释放依赖

引用计数**全局共享、不认场景归属**。切走 A → 公共图标/图集/FairyGUI 包计数掉到 0
→ 下一帧 destroy → B 随后加载拿到已销毁 asset → Sprite 纹理失效 → 静默跳过。
纯时序竞态，所以「来回切几次」才概率复现。

**之前的修复只门控了 `releaseUnusedAssets()` 这一个出口，这条自动释放路径完全没堵**
（`installDirectorAssetReleaseHook` 一直是空函数），所以问题反复出现。

### 改动

**JS（ios2-web-boot.js）**
- 新增 `installAssetReleaseGate()`：hook `tryRelease`，场景切换窗口期内拦截**非 force**
  的释放。**入队延后而非丢弃**——引擎 `_free` 非强制时会先看 refCount，新场景已重新

### 闸门逻辑已用最小复现验证（/tmp/verify_gate.js，按引擎真实语义复刻）

`_free(t,e)` 的条件 `!( !e && refCount>0 && u(t)>0 )` 是关键：非强制模式下会**复检
refCount**。所以拦截后延后执行是安全的——新场景已重新引用的会被引擎自己跳过。
三个场景结果：无闸门 destroyed=true（缺块）／有闸门 destroyed=false（保住）／
真没人要的资源 destroyed=true（**仍然正常回收，不泄漏**）。

### 用户怀疑「是不是我们自己的释放资源代码害的」——核实结论（本轮追加）

逐条查了我们三条释放相关路径，**结论是：我们的显式释放代码不是元凶，那条隐含的
自动释放才是**。

1. `runRuntimeSoftCleanup`（:290）**根本不调用** `releaseUnusedAssets`，
   只跑 `cc.sys.garbageCollect()`（JS 堆 GC）。Cocos 资源是引用计数管理、不吃 GC，
   所以它是安全的。
2. `installRuntimeMemoryHooks`（:368）里 `EVENT_HIDE` / `visibilitychange` /
   console 页面切换 ≥4 这三条触发都只 `scheduleRuntimeSoftCleanup` → `runRuntimeSoftCleanup`
   （GC -only）。**它们不会释放任何 Cocos 资源**，更不会跨实例释放共享资源、
   也不会在切场景暂停时误杀还在用的资源。之前担心的「呆久不操作再切场景触发释放」
   不成立。
3. `releaseUnusedAssets`（:428）开头 `if (!assetReleaseState.shuttingDown) return false`，
   而 `shuttingDown` 只在 `shutdownGame`（:759）真退出登录时置 true，且
   `releaseUnusedAssets('shutdown')` 只从 `shutdownGame`（:779）调用。
   → 我们的显式释放被**正确门控到退出登录**，切场景期间绝不会触发。

真正害事的：`releaseManager.tryRelease` 是引用计数驱动的**自动**释放，每次 `decRef()`
都跑，跟我们任何显式调用无关——之前 `installDirectorAssetReleaseHook` 是空函数，
这条路径完全没堵。`installAssetReleaseGate` 现在 hook 住它、在切换窗口内延后非 force
释放，才是根因修复。

一句话回复用户的判断：**我们自己的释放代码（soft cleanup / releaseUnusedAssets）是
干净的，问题出在 Cocos 自己每次 decRef 就 tryRelease 的隐式路径，现已被闸门兜住。**
