## 修复「切回页面画面显示不全 / UI 贴图丢失」

排查 commit 5ee5f3d（webkit 改善内存占用和释放）引入的问题。

### 结论：根因不在 JS 释放，在 SwiftUI 层

- `ios-cocos/cocos-project/src/ios2-web-boot.js` 的激进释放其实已被后续提交
  （e8b7ac7 / 582bcd9 / bfc29d5）门控住：`releaseUnusedAssets()` 只在
  `assetReleaseState.shuttingDown` 时执行，页面切换不释放。
- 真正的元凶：`MacMultiOpenManagerView.matrixCanvas` 用 `ScrollView + LazyVGrid`。
  懒加载容器只实例化可视区格子，卡片滚出即销毁 `NSViewRepresentable` →
  `dismantleNSView` → `stop()` → WKWebView + WebGL 上下文被拆；滚回来等于重新加载
  整个游戏 → 表现为「部分 UI 贴图丢失 / Canvas 画面被裁切」。多开不限数量时必现。

### reload 黑屏根因（重要，别再踩）

日志关键行：`[ios2-web] canvas backing size 0x0 css=0x0` + 埋点里 `"resolution":"0x0"`。
游戏逻辑全跑完了（assets=69 / ready / stable=true），但 canvas 是 0×0 → 画面全黑。

真因：加了 `MacGameSurfaceHostView` 这一层之后，
SwiftUI 用约束给 host 定尺寸 → host.layout() 给 surface 赋 frame，
但 **AppKit 通过 autoresizing mask 改 subview 尺寸时不会调用 subview 的 layout()**，
而 `MacWebKitGameView` 正是在 `layout()` 里才 `webView.frame = bounds`。
→ WKWebView 一直停在 init 的 `.zero` → `window.innerWidth` = 0 → Cocos 建 0×0 canvas。

为什么只有重载黑屏：首次加载 CDN 冷启动 + 鉴权耗时够长，AppKit 抢在页面 boot 前
完成 layout；重载时缓存全热，页面 739ms 就起来，layout 还没跑。

修法（两处都做）：
1. `MacWebKitGameView` 不再从 `.zero` 起步：`super.init(frame: 270×480)`（9:16
   兜底），init 里立刻 `webView.frame = bounds`。
2. 加 `setFrameSize` 覆盖把 webView 钉回 bounds（零尺寸忽略）——因为 AppKit 的
   autoresizing 路径不触发 `layout()`。
3. `MacGameSurfaceHostView` 同样加 `setFrameSize` 覆盖 + `layout()`，双保险。

### reload 黑屏第二轮：中间宿主视图被撤销

上一轮修完后画布尺寸对了（`canvas backing size 1170x2080 css=585x1040`、
`ratio: 1.7777`），但**仍然黑屏**。说明 0×0 只是其中一个症状。

结论：`MacGameSurfaceHostView` 这层中间 layer-backed 容器是纯粹的麻烦来源——
它既挡住尺寸传递（AppKit 用 autoresizing 改 subview 时不调 subview 的 layout()），
又可能在合成上出问题。**已撤销该层**，`MacEmbeddedGameView` 直接把池里的
`MacWebKitGameView` 交给 SwiftUI，层级回到最初能正常渲染的形态：
SwiftUI → MacWebKitGameView → WKWebView。

保活不再靠宿主，而是靠 `dismantleNSView` 里什么都不做——格子被销毁时视图只是
脱离层级，实例仍活在池里，下次 `makeNSView` 直接返回同一个对象（SwiftUI 会自己
把旧视图摘掉）。这是 NSViewRepresentable 的常规复用写法。

教训：给 WKWebView 套自定义 NSView 容器要非常小心，尺寸和合成两条链路都会断。
能不动层级就别动。

### 第二轮加固 + reload 黑屏修复

reload 按钮第一版走 `pool.reload(accountID:)` + `reloadKey = UUID()`：池子立刻
`removeFromSuperview` + `stop()`，然后才让 SwiftUI 拆除旧宿主。
实测黑屏——立刻 stop 会把 WKWebView 留在「已经脱离窗口层级、但 WKNavigation
仍在飞」的中间态，老 navigation 既收不到 didFail、也不会自己停，新 view 的
start() 会被同窗口里残留的旧资源卡住。

改成延迟驱逐：
- `MacGameInstancePool.requestReload(accountID:)` 只往 `reloadPending` 插一个标记；
- 真正的 stop 推迟到下次 `surface(for:)`（也就是 SwiftUI 已经 dismantle 完旧宿主、
  新宿主 bind 时）。整个生命周期就跟当初没有 pool 时 reload 按钮的语义一致。

`xcodebuild` BUILD SUCCEEDED。

### 第二轮加固

- `MacMatrixGrid.Row.id` 从「本行首实例 id」改为**行号**：关掉一个账号时后面实例
  整体前移，按首实例取身份会导致之后每一行 id 全变、整行格子重建；用行号则只有
  真正跨行的那一个实例会重建。
- `MacGameSurfaceHostView.applyFrame(to:)`：忽略零尺寸 bounds。把 0×0 交给
  WKWebView 会让 WebKit 丢弃 layer backing store，是「画面被裁切」的第二成因；
  首次挂接时先给 270×480（9:16）占位。

### 关键事实（排查过，别再重复查）

- 引擎 `ios2-web-cocos2d.js` 里 `webglcontextlost` 监听数 = **0**，引擎完全不处理
  上下文丢失。
- `device._restoreTexture(unit)` 只是 `bindTexture` 缓存的 `_glID`，不会重建/重传。
- Cocos 默认 `CLEANUP_IMAGE_CACHE`：纹理上传后丢掉 `_image` 源数据。
  ⇒ **真丢上下文时普通 PNG/WebP 贴图无法恢复**，只能靠「不让它丢」。
  若要支持恢复，得显式保留源数据（内存代价）或丢上下文后重建实例。

### 遗留 gap（未修）

WebGL 上下文真丢失时，现有 PVR 恢复只覆盖 ASTC/PVR 纹理
（`scheduleASTCPVRRecovery`），PNG/WebP 等普通纹理没有源字节可重传，仍会丢。
