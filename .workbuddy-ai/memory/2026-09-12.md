### reload 黑屏根因（重要，别再踩）

日志关键行：`[ios2-web] canvas backing size 0x0 css=0x0` + 埋点里 `"resolution":"0x0"`。
游戏逻辑全跑完了（assets=69 / ready / stable=true），但 canvas 是 0×0 → 画面全黑。

真因：加了 `MacGameSurfaceHostView` 这一层之后，
SwiftUI 用约束给 host 定尺寸 → host.layout() 给 surface 赋 frame，
但 **AppKit 通过 autoresizing mask 改 subview 尺寸时不会调用 subview 的 layout()**，
而 `MacWebKitGameView` 正是在 `layout()` 里才 `webView.frame = bounds`。
→ WKWebView 一直停在 init 的 `.zero` → `window.innerWidth` = 0 → Cocos 建 0×0 canvas。

为什么只有重载黑屏：首次加载 CDN 冷启动 + 鉴权耗时够长，AppKit 抢在页面 boot 前
完成 layout；重载时缓存全热，页面 739ms 就起来，layout 还没跑。

修法（两处都做）：
1. `MacWebKitGameView` 不再从 `.zero` 起步：`super.init(frame: 270×480)`（9:16
   兜底），init 里立刻 `webView.frame = bounds`。
2. 加 `setFrameSize` 覆盖把 webView 钉回 bounds（零尺寸忽略）——因为 AppKit 的
   autoresizing 路径不触发 `layout()`。
3. `MacGameSurfaceHostView` 同样加 `setFrameSize` 覆盖 + `layout()`，双保险。

### reload 黑屏第二轮：中间宿主视图被撤销

上一轮修完后画布尺寸对了（`canvas backing size 1170x2080 css=585x1040`、
`ratio: 1.7777`），但**仍然黑屏**。说明 0×0 只是其中一个症状。

结论：`MacGameSurfaceHostView` 这层中间 layer-backed 容器是纯粹的麻烦来源——
它既挡住尺寸传递（AppKit 用 autoresizing 改 subview 时不调 subview 的 layout()），
又可能在合成上出问题。**已撤销该层**，`MacEmbeddedGameView` 直接把池里的
`MacWebKitGameView` 交给 SwiftUI，层级回到最初能正常渲染的形态：
SwiftUI → MacWebKitGameView → WKWebView。

保活不再靠宿主，而是靠 `dismantleNSView` 里什么都不做——格子被销毁时视图只是
脱离层级，实例仍活在池里，下次 `makeNSView` 直接返回同一个对象（SwiftUI 会自己
把旧视图摘掉）。这是 NSViewRepresentable 的常规复用写法。

教训：给 WKWebView 套自定义 NSView 容器要非常小心，尺寸和合成两条链路都会断。
能不动层级就别动。

### 帧率生效的验证手段（同轮补充）

「怎么确认帧率真的生效」的答案，三种粒度：

1. **肉眼**：设置页「显示实时帧率角标」（`ios2.showFrameRateHUD`）→ 画面左上角
   `15 FPS  目标 15` / `98 Hz  vsync`。游戏 FPS 数的是 Cocos 主循环（`EVENT_AFTER_UPDATE`），
   vsync 数的是 `requestAnimationFrame`——**两件事**。
2. **一次性回读**：设置页「校验」按钮 → `账号：游戏 15 / 目标 15 / 注入 15 / vsync 98`。
   走 `WKWebView.callAsyncJavaScript`（**唯一能 await Promise 的通道**，
   Swift 侧已被 refine 成 async 版，没有 completion 版）。
3. **Web Inspector**：`defaults write com.xyzw.ios2.webkit.macos
   ios2.debug.webInspector -bool true` → `webView.isInspectable = true` →
   右键检查元素，看 `[ios2-web] target frame rate 30`。

坑：WKWebView 的 `console.log` **不进 Xcode 控制台**（无 console 桥接），所以
WebRuntime 的启动日志只能在 Web Inspector 里看；原生侧统一用 NSLog。

- rAF 在窗口被遮挡/后台时会被 WebKit 完全停掉 → 自检的 Promise 永不 resolve，
  `evaluateWithTimeout` 必须带 3s 超时（用 TaskGroup 竞速）。

### 第一版 HUD 算错了：用 rAF 数的是 vsync 不是游戏帧

截图示例（100Hz 显示器 + 15 FPS 设定）：HUD 显示 `98 FPS  目标 15`——
`98` 是显示器刷新率，跟游戏无关。

引擎在非 30/60 帧率档位下用 `_setAnimFrame` 把 `window.requestAnimFrame` 替换成
`setTimeout(_frameTime)`（`1000/frameRate` ms），主循环真的被节流到目标 FPS。
但**标准** `requestAnimationFrame`（首字母大写）引擎不动，所以基于 rAF 写的
HUD 一直显示显示器刷新率。

修正（采样器从 rAF 改为 `cc.director.on('director_after_update', …)`）：
- 采样器**始终常驻**（`atDocumentStart`，不动 HUD 开关），单独显示 vsync 作辅助。
- HUD 只控制 DOM 角标和 setInterval；采样器不动。
- 校验脚本同样基于采样器算 `game`/`vsync`。
- 长会话用前后差分而非累计除以总时长，避免长时间后整数除法向下归零。

### HUD 改完不显示的坑（第二轮）

角标脚本开头写了 `if (!window.__ios2Fps) return 'sampler-missing'`，而采样器是
**启动时**注入的——对「改动前就已经在跑的实例」页面里没有采样器，于是直接 return，
表现就是"开关开了但什么都不显示"（旧版自带 rAF 循环所以能在老实例上现装）。

修法：`overlayShowScript = samplerScript + overlayBodyScript`，显示脚本**自带采样器
补装**，任何页面都能现装。另加 `document.body` 缺失时 50ms 重试（documentEnd 时
body 可能还没建好）。

### 角标"开关开着进游戏却不显示"（第三轮）

根因：**在 `makeWebView()` 里读开关**——但实例视图是 `MacGameInstancePool`
池化复用的，视图可能早在开关打开之前就创建好了，那次判断拿到的是过期旧值。
bootstrap 之所以没事，是因为它在 `start()` 里每次进游戏前才登记。

修法：采样器 + 角标**一律挪到 `start()`**，跟 bootstrap 一起在
`webView.load()` 之前重新登记（视图创建时不再注入任何帧率脚本）。
⇒ 通则：**凡是依赖用户设置的注入，都不能在 init/makeWebView 里读开关。**

### 真正的根因：池化实例没有第二次注入机会（第四轮）

挪到 `start()` 仍不显示，因为多开实例走 `MacGameInstancePool.surface(for:)`：
已存在的实例直接 `return existing`，**不重跑 `start()`**——所以"重新打开窗口"
根本没有第二次注入机会，WKUserScript 那条路对池化/重载实例天生不可靠。

最终方案：角标当**运行时状态**处理，跟群控捕获开关同款，一律走
`evaluateJavaScript`，在两个"一定会发生"的时机补：
1. `didFinish`（文档加载完）
2. `MacGameInstancePool.surface(for:)` 返回 existing 时（池化实例重新挂回）

设置页开关 → `MacFrameRate.syncHUD()` 广播。WKUserScript 那份保留作兜底。
另加 `diagnosticScript` 回读 `{sampler,hook,element,connected,display,updater,body,cc}`
并在 didFinish NSLog，用于区分"脚本没跑" vs "跑了但被摘/不可见"。

⇒ 通则：**运行时开关型状态不要指望 WKUserScript**，它只在导航那一刻生效；
池化复用 + 重载会让那条路彻底失效。参照 `MacInputSyncController.refreshCapture`
在 didFinish 补一次的写法。

### 最终真凶：cc.game.config 在文档加载完时还是 null（第五轮）

日志铁证：
```
JS error: getFrameRate@ios2-game://app/cocos2d.js:17190:33
update@user-script:6:52:31
fps hud diag: {...,"element":true,"connected":true,"display":"block","updater":false}
```
`cc.game.getFrameRate()` 的实现就是 `return this.config.frameRate`（cocos2d.js:17190），
而 `cc.game.config` 要等 `cc.game.run(option)` 之后才有值——文档加载完（documentEnd /
didFinish）时它还是 null，直接 TypeError。异常冲出 IIFE ⇒ `setInterval` 那行没执行
⇒ 元素建了、挂上了、但 textContent 空 ⇒ 看不见。手动切开关能显示，纯粹是因为那时
游戏已经 boot 完、config 有值了。

修法三条：
1. 读目标值先判 `cc.game.config` 存在，否则回退 `__IOS2_GAME_INSTANCE__.frameRate`。
2. `update()` 整体包 try/catch——单次渲染失败不能带走定时器。
3. **先 `setInterval` 再首次 `update()`**（顺序反了，首帧抛异常就把定时器带走）。
   `applyScript` / `verifyScript` 里的 `setFrameRate` / `getFrameRate` 同样加 config 护栏。

⇒ 通则：**注入到游戏页面的脚本必须在"引擎可能还没初始化"的前提下写**。
`cc` 存在 ≠ `cc.game.config` 存在；引擎提供了函数 ≠ 现在能调。
注入脚本首帧就崩是这个项目反复踩的坑，凡是读引擎状态的都要 try/catch + 守卫。

另加自愈：角标 update 里检查 `element.isConnected`，被页面摘掉就 append 回去
（不需要 MutationObserver，update 本来就 500ms 跑一次）。

验证手段：用 python 从 Swift 抽出 `"""` 字符串 → node `--check` 语法 →
假 DOM + 假 rAF/主循环驱动跑冒烟（98Hz vsync + 15Hz 主循环 →
HUD 输出 `16 FPS 目标 15 / 100 Hz vsync`，采样器补装 + hook=true 均通过）。
注意脚手架坑：假 `window` 上要挂 `cc`（`window.cc` 而非只是 globalThis.cc），
假 rAF 要在触发后清空 pending 队列，否则回调会指数复制。

### Cocos 2.4.9 `setFrameRate` 的缺陷（ios2-web-cocos2d.js:17181 / 17354）
```js
setFrameRate(t){ config.frameRate=t; cancelAnimFrame(_intervalId); _paused=true;
                 _setAnimFrame(); _runMainLoop(); }   // _runMainLoop 里立刻 _paused=false
t=(i)=>{ if(!e._paused){ e._intervalId=requestAnimFrame(t);   // 旧循环看到 false → 复活
           if(30===a && (s=!s)) return;                        // a=本循环启动时捕获的帧率
           r.mainLoop(i); } };
```
旧循环只有见到 `_paused===true` 才停止续命 → 运行时改帧率可能残留多条循环；
且它们共写模块级 `_lastTime`，把 `_stTimeWithRAF` 的节流计时搅乱（45 档只跑出 34）。
**仿真结论**：干净切换下 cancelAnimFrame 是有效的，残留需要特定时序；两种故障要分开量。

### 已落地的修法（MacFrameRate.swift）
1. `applyScript` **不再调 `cc.game.setFrameRate()`**，改成 `pause() → 等 max(120ms, 3×帧时长) → 写 config.frameRate → _setAnimFrame() → resume()`。
   收尾必须用公开 `resume()`（会 `_restore` 音频 + 重置 deltaTime），不能用内部 `_runMainLoop()`，
   否则 `pause()` 的 `_break()` 会把音频卡死。原本就是暂停的实例不恢复（`wasPaused` 判断）。
   已是目标值直接 `noop`，避免每次开设置页都抖一下。
2. 主循环去重守卫 `installMainLoopGuard()`：包住 `cc.director.mainLoop`，
   同一 rAF 时间戳的重复调用丢弃并计入 `state.dupes`。
3. `state.hooks` 计数器：区分「多条主循环」（dupes>0）与「监听器挂重了」（hooks>1）——后者会让读数成整数倍虚高。
4. 校验输出新增 `dupes/s` 和 `hooks`，超标时报告里打 ⚠️。

## 真机验证结果（100Hz 屏，单实例 15小惜.bin）
每次切档回执均为 `ok-restart:N`，**无任何 ⚠️** → 重复主循环 0/s、监听器 ×1，
之前 `60 档测出 196` 的故障已确认修复（现在 60 档 = 97 = vsync）。

实测对照（设定 → 实测）：
15→15、24→23、30→**49**、45→44、60→**97**、90→81、120→97（vsync 96~100 波动）

**根因（重要）**：`_setAnimFrame()`（ios2-web-cocos2d.js:17316）只有 30/60 走裸 rAF 不节流，
其余走 `_stTimeWithRAF`。所以：
- 15 / 24 / 45 = 精确命中（setTimeout 节流）
- 30 = 隔帧跳过 → 实际是**刷新率的一半**（60Hz 屏 = 30，100Hz 屏 = 49）
- 60 = 裸 rAF → 实际是**刷新率全速**（100Hz 屏 = 97）
即 30/60 两档是"相对显示器"的，不是绝对值。100Hz 屏上想精确控帧只能用 15/24/45。

**60 档不能靠节流封到 60**：`_stTimeWithRAF` 的 16.67ms 会被 vsync 量化成 20ms → 只有 50，
比裸 rAF 的 97 更差。所以高刷屏上 60 档注定跑满屏幕，不必也不能修。
30 档若改走 `_stTimeWithRAF` 约能到 30~33，但要覆盖引擎的 `window.requestAnimFrame` 指派。

## 30 档精确化（用户确认要做）
`installExactRate()` 加在 `samplerScript`（必须早于引擎 boot 的 `_runMainLoop`，且后续任何
`resume()` 都会再走一遍）。原理：包住 `cc.game._runMainLoop`，启动前把 `config.frameRate`
临时写成 **29.999** 并重跑 `_setAnimFrame()` —— 29.999 不在 {30,60} 里，引擎自动切到
`_stTimeWithRAF`（_frameTime=33.3ms），`30 === a` 也就不再命中隔帧跳过；`finally` 里还原成 30，
`getFrameRate()` 对外仍是 30。
**只改 29.999 不够，必须同时重跑 _setAnimFrame()**，否则调度器还停在裸 rAF 上，会变成 97。

### 仿真结论（end-to-end，真实 samplerScript + 仿真引擎，100Hz）
- 不打补丁：30 档 45~47/s（与真机 49 吻合）
- 打补丁：30 档 **30/s**，60 档 91~97/s（不受影响）
- 反复切档 30→45→30→15→30→60→30：实测 30/44/30/14/30/91/30，重复帧全程 0，无累积

### 旧 setFrameRate 路径的泄漏已在仿真里复现
同一串切档用 **旧 `setFrameRate`**：60 档跑到 **183/s**（≈2×92），用**新 applyScript**：91/s。
根因是 30 档的 `_stTimeWithRAF` 返回 setTimeout id，一旦回调已排进 rAF 队列，
`cancelAnimFrame`(=clearTimeout) 就取消不掉 → 旧循环复活。
**pause→等待→resume 正是靠 `_paused=true` 让旧回调自然退出才避开的** —— 两个修法互相印证。

## 快速连点切档导致自检读数污染（第二轮真机日志）
现象：「注入」总比「目标」快一档（15→注入24、30→注入45、45→注入60），实测普遍偏低
（45 档只测出 28），静置后连续三次校验一路爬升 68→79→97。
**不是故障，是任务重叠**：
- `applyScript` 先 `pause()` 再等 120~400ms 才 `resume()`，后一次切档的暂停窗口
  压进前一次 1 秒采样窗口 → 实测被拉低
- `applyScript` 一进来就写 `__IOS2_GAME_INSTANCE__.frameRate`，但要等一会儿才写
  `config.frameRate` → 自检读到「注入=下一档、目标=当前档」
- 最后三次 68→79→97 是没有新切档干扰后的真实读数（97 = vsync，正确）

### 修法（MacFrameRate.swift）
1. `pendingWork: Task?` + `workGeneration: Int` 串行化：新一轮先 `cancelPendingWork()`
   （cancel + 世代号 +1）。网页的 `evaluateAsync` 发出去收不回，光 cancel 拦不住
   已飞出的采样，必须用世代号把过期结果丢掉。
2. 自动自检前 `Task.sleep(700ms)` 等主循环爬坡完再采样。
3. `applyScript` 在等待**之后**再写一次 `__IOS2_GAME_INSTANCE__.frameRate`，
   让「注入」和「目标」同一时刻一起变（开头那次保留，供等待期间启动的新实例读取）。
4. 新增 `verifyAndLog()` 给设置页按钮用：同样先作废上一轮，期间改了帧率就返回
   「（已被新的帧率改动取消，请重新校验）」，不打误导人的数字。

### 教训
带「暂停→等待→恢复」语义的注入脚本，自检必须串行化并留出稳定期，
否则测到的是重启过程而不是稳态帧率。真机验证时每次切档后应静置 ~2 秒再读。

## 「设 45/60/90 → 重新登录后目标变 30」根因与修法
### 根因
游戏 bundle 处理登录响应时会把自己的默认值 30 塞进来（`ios2-login.js:210` 注释明写）。
原生 Cocos(jsb) 壳在 `ios-cocos/cocos-project/main.js` 有两道防线：
1. 包住 `cc.game.setFrameRate`，`requestedFrameRate !== preferredFrameRate` 时直接改回用户值（:654-657）
2. `window.__ios2SchedulePerformanceRestore(reason)` —— 登录后 0/500/2000ms 三次恢复（:664）
`ios2-login.js:215` 会调这个钩子，但**它只定义在 main.js（原生壳入口），WebKit 壳走
`ios2-web-boot.js`，从来没定义过** → `typeof` 判断为 undefined → 恢复永不执行 → 30 一直留着。

### 修法（MacFrameRate.swift 的 samplerScript）
1. `installLoginGuard()`：包住 `cc.game.setFrameRate`，`fps !== preferredRate()` 时不转给引擎，
   回传 `frameRateBlocked`。preferred 来自启动注入的 `__IOS2_GAME_INSTANCE__.frameRate`，取不到就不干预。
2. 补上 `window.__ios2SchedulePerformanceRestore` 定义（0/500/2000ms 三次），
   内部 `restorePreferred()` 走「pause→等→改 config→_setAnimFrame→resume」，
   捕获 `wasPaused` 避免把暂停中的实例唤醒。管得到"绕过接口直接写 config.frameRate"的情况。
3. 原生新增两个 NSLog case：`frameRateBlocked` / `frameRateRestore`。

### 仿真验证（login_guard.mjs）
- 游戏调 setFrameRate(30)、用户设 90 → 目标保持 90，回传 blocked ✓
- 游戏直接写 config.frameRate=30（守卫管不到）→ 登录钩子恢复到 90 ✓
- 用户改设定为 45 后游戏同步调用 → 目标 45，不被拦 ✓

### 教训
原生壳(jsb, main.js) 和 WebKit 壳(ios2-web-boot.js) 是两套入口，
凡是在 main.js 里做的兜底/守卫，都要确认 WebKit 侧有没有对应实现。
`ios2-login.js` 用 `typeof x === 'function'` 做可选调用，缺实现时静默跳过，很难发现。
